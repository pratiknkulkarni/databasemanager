# Ecosystem Constraints (Go)
- **Goroutine/Channel Patterns:** Detect any goroutines spawned without bound or context: background `go func` handlers or loops that never check `ctx.Done()` become zombie tasks. Unbuffered channel sends without concurrent receivers lead to deadlocks or leaks (goroutines block forever, wasting memory). Look for worker pools where producers and consumers can block each other (e.g. feeding and draining channels on the same goroutine) – these cause gridlock under load. **Flag:** unbounded fan-out (launching infinite goroutines per request), channels never closed, missing cancellation on loops, and waiting sends on full channels; all are DoS/race vectors.  
- **Shared-State Races:** Identify all shared maps, slices, or globals accessed by multiple goroutines. Any concurrent read/write without locks/atomic invites races that crash or corrupt state. For example, unsynchronized map writes lead to runtime panic (which an attacker can trigger) or allow TOCTOU exploits (check-then-use without lock). **Flag:** global counters or caches without `sync.Mutex`/`atomic`, use of non-`sync.Map` maps in handlers, or split-lock logic (unlock too early). Race conditions can yield privilege leaks (e.g. double-spend or stale permissions).  
- **Context & Lifecycle:** Audit for missing context propagation. All spawned goroutines should derive from the request’s `ctx`; absence means they outlive the request and ignore cancellation (kill-switch leftover). **Flag:** use of `context.Background()`/TODOContext in request code, loops/selects without `case <-ctx.Done()`, and detached retry loops. Ensure HTTP requests and DB calls use contexts with timeouts; otherwise slow or hanging operations (tarpits) stall the service.  
- **Goroutine Amplification:** Check for patterns allowing exponential growth: e.g. on error, code that immediately retries by spawning new goroutines without limit or backoff. Also look for HTTP/2 rapid-reset issues (pre-patch CVE-2023-39325): request handlers that continue after client resets. A malicious client can open many streams and reset them to spawn endless handler goroutines beyond `MaxConcurrentStreams`. **Flag:** incomplete cancellation on error paths and any unbounded retry/fan-out loops.  

## Trust Boundary & Auth Enforcement

- **Client-Controlled Auth Fields:** Never trust user-supplied fields for identity or access control. If an incoming JSON or header contains `userID`, `role`, `admin`, etc., treating that as auth is direct privilege escalation. **Flag:** authorization checks based on data from the request without server-side verification (e.g. using an HTTP parameter or JWT claim without signature validation).  
- **Tenant/Session Scoping:** Each request must carry its own tenant/user context; ensure no cross-request state retention. Any DB query or cache lookup must include the tenant ID or user scope from the authenticated context. Missing a filter (e.g. forgetting `WHERE tenant_id = ?`) quietly leaks data across tenants. **Flag:** shared caches keyed only on resource id (missing tenant key), use of global session objects, or context values (like tenant ID) that are not refreshed per request.  
- **Internal API Trust:** Do not implicitly trust internal calls. Even services marked “internal” or authenticated by a cookie can be invoked in unexpected ways. Every service boundary should enforce auth/ACL. **Flag:** RPC or handler endpoints with no auth checks (assuming traffic is internal), or use of forwarded headers (`X-Forwarded-*`) as trust. Check for missing enforcement on admin/debug endpoints.  
- **Context Manipulation:** Context values should not be overloaded for trust. Do not use `context.WithValue` to smuggle unverified identity/role info through layers without revalidation. **Flag:** business logic that reads auth/tenant from context that originated in middleware without fresh security checks, or `ctx` mutated mid-request in an untrusted way (e.g. overwritten by plugins).  

## Panic and Failure Safety

- **Attacker-Triggered Panics:** Identify code paths where user input can trigger a panic (nil-pointer deref, out-of-range slice, failed type assertion, or parsing error). A panic either crashes the goroutine or entire server. For DoS, any uncaught panic is exploitable. **Flag:** indexing into slices or maps using user data, pointer dereferences on potentially nil structs, or parsing operations (e.g. JSON with unexpected type) without checks.  
- **Recover Misuse:** Using `recover()` broadly can hide failures. Ensure recover blocks do not swallow security-critical panics. A `defer func(){ if r := recover() { … } }` that logs and continues can mask attacker-caused exceptions and leave partial state. **Flag:** any `recover()` that does not rethrow or explicitly abort the request on critical sections (e.g. authentication, input parsing). Recover should lead to request termination, not silent fail-open.  
- **Fail-Open Error Handling:** Check every error path: the default should be fail-closed. Examples: `if err != nil { continue }` without stopping the flow can bypass checks. **Flag:** logic that ignores or logs an error then proceeds (e.g. missing `return` after sending an error to channel, as in a nil-resp HTTP GET), or functions that return `true`/`success` on error.  
- **Partial State Corruption:** Audit transactional or multi-step operations: if an error occurs mid-way, state should not be committed. **Flag:** missing rollback/cleanup on error paths. For example, locking resources then error-ing out without `defer unlock` leaves deadlocks or inconsistent state. Panics in middle of DB writes without transaction rollback can leave data half-updated.  

## Resource Exhaustion / DoS

- **Unbounded I/O:** Reading user data without limits is a direct memory DoS. Flag uses of `io.ReadAll`, `json.Decoder`/`xml.Decoder` on unlimited streams, or large `bufio.Scanner` loops with no `Size()` cap. Attackers can send multi-GB payloads or endless streams (decompression bombs). **Constraint:** enforce `io.LimitReader` or `MaxBytesReader`, set sensible `Content-Length` bounds, or stream/discard early.  
- **Slowloris/Timeouts:** Servers and clients must use deadlines. Any `http.Server` or `http.Client` lacking timeouts is vulnerable to slowloris: a client opens a connection and never finishes headers/body, tying up a thread. **Flag:** `http.Client` with no `Timeout` or transports with default unlimited idle conns; `Server` handlers not checking `ctx.Done()`.  
- **Amplification DoS:** Patterns that amplify requests: e.g. HTTP handlers that spawn child goroutines per request without limit (worker pools missing size caps). **Flag:** fan-out on each request (e.g. dynamic concurrency with no semaphore). Also check retry loops: an attacker causing repeated failure (e.g. auth failure) may trigger an endless retry storm.  
- **Regex/CPU Abuse:** Regexes on user input can be catastrophically slow if crafted maliciously (ReDoS). Identify complex patterns or unbounded `regexp.Compile`/`MatchString` on user data. **Constraint:** use timeouts or RE2 (Go’s default is RE2, so limited, but custom regex engines can block). Also flag heavy CPU loops on user data.  
- **Connection/Descriptor Exhaustion:** Attackers can exhaust sockets or FDs by opening many connections or files. Check for lack of connection pooling limits (e.g. `MaxIdleConnsPerHost` unset) and for file opens in handlers (unbounded). **Flag:** any code using `http.Get` or DB/sql without connection limits, no proper `defer Close()`, or heavy use of `os.Open` on dynamic paths.  

## Serialization & Input Integrity

- **Unstructured Deserialization:** Unmarshaling directly into domain structs is risky. An attacker can set any exported field (including hidden logic fields) if tags permit. **Flag:** `json.Unmarshal(data, &Entity)` where `Entity` has sensitive fields (IDs, flags). Better decode into an API-specific DTO and map manually.  
- **JSON Case/Key Ambiguity:** Go’s JSON parser is case-insensitive and accepts duplicate keys (last one wins). Attackers exploit this by sending fields with different casing or duplicates to override values. **Example:** sending both `isAdmin` and `IsAdmin` results in the last value applied. **Constraint:** enforce strict unmarshaling (e.g. use `Decoder.DisallowUnknownFields`, avoid relying on tag-less matching), and validate key uniqueness manually.  
- **Unknown Fields & Type Confusion:** By default JSON/XML/YAML allow unknown fields. This can hide injected data. **Flag:** use of `map[string]interface{}` or `interface{}` in parsing; missing field validation after unmarshal. Also watch for XML parsers that skip unexpected data. **Constraint:** explicitly reject or check unknown keys, and validate all required fields.  
- **Implicit Conversions:** Number and string type mismatches in JSON can be coerced (e.g. `"true"` to bool). Attackers can supply wrong types to alter logic. **Flag:** any lenient decoding (like `,omitempty` usage). Use `json.UnmarshalStrict` (JSONv2) or manual parsing to avoid surprises.  
- **Cross-Format Confusion:** Be wary of parsing multiple formats: e.g. an XML parser may happily parse a JSON-looking string as XML by ignoring gibberish, enabling bypass (like HashiCorp Vault’s CVE-2020-16250). **Constraint:** strictly enforce content-type and use format-specific parsers. No automatic sniffing.  
- **Serialization Panics:** Deeply nested input (recursive structs, heavy YAML anchors) can blow the stack or heap. **Flag:** YAML libraries (go-yaml) parsing user data can be DoS vectors. Restrict document size and depth if possible.  

## Secrets & Observability

- **Sensitive Logging:** Ensure no secrets (passwords, tokens, keys) are logged or returned. **Flag:** any `log.Printf` or `fmt.Println` on raw request structs, headers, or error values that may include auth credentials. Also check audit logs or metrics to ensure they sanitize sensitive tags.  
- **Stack Trace Exposure:** Recover or error handlers that write `panic` or `err` directly to HTTP response leak file paths and code. **Constraint:** never send raw panic text or `errors` to client; handle internally and return generic error.  
- **Debug/Profiling Endpoints:** Anything under `/debug/pprof`, `/metrics`, or similar should be disabled or secured in production. They expose heap, goroutines, and other internal state. **Flag:** inclusion of `net/http/pprof` or similar handlers with no auth guard.  
- **Environment/Config Leakage:** Avoid printing environment variables or configuration (which may include DB creds or tokens). **Flag:** `os.Getenv` output to logs or error, or code that dumps `os.Environ()`.  
- **Telemetry Data:** Tracing systems or logging libraries often attach HTTP headers (like `Authorization`, `Cookie`) to logs or spans. **Constraint:** configure tracing to exclude auth tokens and PII. Be skeptical of middleware that dumps full headers in JSON format.  

## Architectural Abuse Patterns

- **Hidden Auth Logic:** Check that authorization is enforced at every interface. Auth checks buried only in middleware or DB layer can be circumvented if another path skips that layer. **Flag:** business logic paths (handlers, jobs, background tasks) that perform actions without explicit re-check of user permissions.  
- **Mixed Layers:** Business logic should not rely on transport-layer assumptions. For example, using HTTP path params or graphQL queries directly to decide auth. **Flag:** any logic that trusts the presence of a route or flag instead of checking a subject’s privilege.  
- **Global Mutable State:** A shared global (e.g. a user cache, session store, rate-limit bucket) used across tenants/users without proper partitioning can cause cross-tenant access. **Constraint:** each global resource must include request-specific keys.  
- **Implicit Dependencies:** If handler A calls service B expecting B to authenticate, ensure this is enforced. Similarly, shared libraries should not assume the caller did auth. **Flag:** any service-to-service call without mutual TLS or token check.  
- **Feature Flags & Config:** Unsafe flags (e.g. debug mode toggles, beta features) that can be controlled by user requests or environment should have strict approval logic. Attackers might switch on unsafe code paths.  
- **Observability Coupling:** For example, metrics or status endpoints that reveal rate limits, queue lengths, or user activity can aid an attacker. **Flag:** verbose stats or health endpoints that expose internal state to unauthenticated clients.
